# 要件定義書

## 1. AIエージェント概要

本AIエージェントは閉塞NW環境でAIエージェントを開発するためのAIエージェントフレームワークとして開発する。

AIエージェントはOpenWebUIをフロントエンドとして利用し、LiteLLMを介して実行される AI Agent Platformとして提供する。

単一のチャットボットではなく、ツール利用・ナレッジ検索・ファイル操作・ドキュメント生成・ワークフロー実行を行うエージェントプラットフォームとして構築する。

## 2. AIエージェント開発の目的

以下のユースケースを満たすことができるAIエージェントの開発のため、AIエージェントの共通機構を開発する。

- 社内ナレッジ検索
  - あらかじめ設定されたRAGから社内ナレッジを検索し、ローカルLLMを利用して回答を生成することができる。
  - キーワード検索、セマンティック検索のどちらも対応できる。
- ドキュメント活用
  - ファイルアップロードしたドキュメント（Excel、Word、PPT、PDF、Textベースの資料）を読み込み、ルールの応じたチェックや提言ができること。
  - 比較結果や提言をmarkdown形式で出力して回答したり、出力結果のmarkdownを指定したフォーマットでファイル生成（Excel、Word、PPT、PDF等）ができること。
- ソースコード生成やレビュー支援
  - 設計書や実施要領、規約、レビュー観点を読み込み、ソースコード生成や生成されたソースコードに対して自律的にレビューできること。
- テスト項目抽出、テスト項目レビュー、テストケース生成やテストコード生成
  - 設計書やソースコード、テスト観点等を読み込み、テスト項目の抽出、レビューやテストケース生成、テストデータ作成の支援、テストコードを生成することができる。
- QA対応支援
  - 与えられたドキュメントと別部署からの問い合わせ内容に対して、回答の生成や回答内容の文言チェック等ができること。
- 手順書生成
  - 指示された内容に沿った手順書（操作手順書や、運用マニュアル等）を生成できること。

AIエージェント開発者が各ユースケースを満たすために簡易な設定ファイルやプロンプトの修正でAIエージェント開発ができるように下記の共通機能を開発する。

- 利用者毎セッション管理
  - 長期会話履歴を保持できる。
  - 短期会話履歴を保持できる。
- セキュリティ管理
  - ガードレール設定選択可
  - ユーザ権限に応じて、アクセス制御が行えること。また、ユーザ追加・変更に
- モデル管理
  - ユーザの要求に応じてローカルLLMを動的に選択することができる。
  - 生成された回答が正しいかどうかを評価することができる。
- ツール管理
  - ツールを動的に選択することができる。
  - ツールを設定ファイルで追加することができる。
- プロンプト管理
  - プロンプトを用意に変更できる。
- ログ管理
  - 障害ログ、監査ログが取得できる
  - トラブル発生時に障害原因をトレースすることが可能。
- モニタリング管理
  - ローカルLLMモデルのトークン量を計測することができる。
- 将来的な機能拡張
  - このAIエージェントが将来パブリッククラウドのAIエージェントサービス（例えば、AWS Bedrock AgentCore）でも動作可能な拡張性を担保する。


また、AIエージェント開発者がローンチしやすいように、Dockerビルド～コンテナデプロイまでの手順は事前に用意し、極力AIエージェントの制御部分でPython等のプログラム開発が必要なることは避けれるようにすること。

### 3. 機能要件

#### FR-001 OpenWebUI連携（フロントエンドインターフェース）

AIエージェントは OpenWebUI からのリクエストを標準インターフェースとして受け付け、応答を返却できること。

- メタデータ連携（Pipe Function対応）
  - OpenWebUI側の Pipe Function を介して渡される以下の識別子・制御情報をリクエストから抽出し、エージェント実行コンテキストへ引き渡すこと。
    - `user_id`（実行ユーザ識別子）
    - `chat_id`（セッション・スレッド識別子）
    - `file_id`（添付ファイル識別子・複数指定可）
    - `role`（ユーザ権限ロール）
    - `conversation history`（会話履歴）
    - `stream mode`（ストリーミング応答の有効・無効フラグ）
- モデルIDによるエージェントルーティング
  - リクエストされたモデルID（例：`agent-knowledge`、`agent-codereview` 等）に基づき、対応する設定ファイル（YAML）およびワークフローを動的に選択して実行すること。

#### FR-002 LiteLLM連携（LLM抽象化・動的モデル選択）

AIエージェントは LiteLLM を介して各種 LLM と通信し、用途や設定に応じて利用モデルを切り替えられること。

- マルチプロバイダ対応
  - エージェントのコアコードを変更することなく、LiteLLM の設定およびエージェント設定ファイル（YAML）の記述のみで接続先 LLM を変更できること。
  - 対応対象例：Ollama、vLLM（ローカルLLM）、OpenAI、Azure OpenAI、Amazon Bedrock（Claude）、Google Vertex AI / Gemini
- ワークフロー内での動的モデル使い分け
  - 1つのワークフロー内であっても、役割ごとに異なるモデルを指定できること（例：Planner は推論重視モデル、Executor はコード生成特化モデル、Reviewer は別モデル等）。

#### FR-003 AIエージェント自律実行（コア制御）

AIエージェントは与えられた指示とコンテキストに基づき、以下の思考・実行サイクルを自律的に遂行できること。

- タスク分解と計画立案（Planning）
  - ユーザからの複合的な要求を解釈し、達成に必要なサブタスクへ分解して実行計画を立てられること。
- ツール選択とパラメータ生成（Tool Calling）
  - 利用可能なツール一覧から適切なツールを選択し、必要な引数を生成して実行・結果取得ができること。
- 自己評価・レビューと修正ループ（Reflection）
  - 生成した回答やソースコード・ドキュメントを、指定された規約やレビュー観点に基づき自律的に評価し、基準を満たさない場合は修正を再実行できること（最大リトライ回数制限付き）。

#### FR-004 Difyナレッジ検索（RAG連携）

AIエージェントは外部ナレッジ基盤である Dify の Knowledge API と連携し、社内情報を検索・参照できること。

- 検索方式の柔軟な選択
  - ユースケースや設定に応じて、キーワード検索、セマンティック検索（ベクトル検索）、ハイブリッド検索を選択・実行できること。
- ナレッジベース（Dataset）の指定とフィルタリング
  - エージェント設定またはユーザ権限に応じて、検索対象とする Dify のナレッジベースID（FAQ、社内文書、設計資料、過去ナレッジ等）を動的に指定・制限できること。
  - 検索結果には出典元（ドキュメント名・該当箇所・スコア）を含め、回答時の根拠提示に利用できること。

#### FR-005 ファイル解析（マルチフォーマット入力）

AIエージェントは OpenWebUI 等からアップロードされた各種ファイルを読み込み、テキストや構造化データとして解析できること。

- 対応ファイル形式
  - ドキュメント系：PDF、Word（.docx）、Excel（.xlsx）、PowerPoint（.pptx）
  - テキスト・データ系：Markdown（.md）、AsciiDoc（.adoc）、プレーンテキスト（.txt）、CSV、JSON、各種ソースコードファイル
  - 画像系：PNG、JPEG 等（ローカルOCRまたはマルチモーダルVLMによる文字・図表認識）
- 解析モードの切り替え
  - ファイル全文の一括読み込みだけでなく、大容量ファイルに対応するためのページ指定抽出、シート指定抽出、チャンク分割検索を行えること。

### FR-006 ドキュメント生成（マルチフォーマット出力）

AIエージェントは生成したMarkdown等のテキストコンテンツを、業務で利用可能な各種ファイル形式へ変換・生成できること。

- 対応出力形式
  - Markdown（.md）、Word（.docx）、Excel（.xlsx）、PowerPoint（.pptx）、PDF（.pdf）
- テンプレート適用・書式制御
  - 社内標準の表紙・ヘッダ・フッタ・スタイルを定義したテンプレートファイルを読み込み、その書式に沿ってドキュメントを生成できること。

### FR-007 ファイル受け渡し・ダウンロード（MCPサーバー連携）

AIエージェントはアップロードファイルの取得および生成ファイルの配布を、ファイル管理用 MCP サーバーを介して安全に行えること。

- ファイル蓄積と参照
  - アップロードされたファイルやエージェントが生成したファイルを MCP サーバー上のストレージ領域へ保存し、`file_id` をキーとしてエージェントの各ツールから参照できること。
- 署名付きURLによるダウンロード提供
  - 生成されたファイルについて、有効期限付きの署名付きダウンロードURLを MCP サーバーから発行し、OpenWebUI のチャット画面上にダウンロードリンクとして提示できること。

### FR-008 ワークフロー制御（設定駆動オーケストレーション）

AIエージェントは複数のエージェントや処理ステップの実行順序・連携方法を、Pythonコードの改修なしに設定ファイル（YAML等）で定義・変更できること。

- ワークフローパターンのサポート
  - 単一エージェント実行（Single Agent）
  - 順次実行パイプライン（例：Planner → Executor → Reviewer）
  - 条件分岐および差し戻しループ（例：Reviewer が NG と判定した場合に Executor へ差し戻す）
  - 並列実行（複数の観点からの同時レビューや複数ナレッジの同時検索）
- エージェント間コンテキスト受け渡し
  - 前段のエージェントの出力結果や中間成果物を、次段のエージェントの入力として構造化して引き渡せること。

### FR-009 プロンプト管理（外部化・ホットリロード）

AIエージェントの振る舞いを規定するシステムプロンプトおよび各種テンプレートを、アプリケーションコードから分離して管理できること。

- 外部ファイル管理
  - エージェント単位・ロール単位（Planner用、Reviewer用等）に独立したテキスト／Markdownファイルとして管理できること。
- 無停止反映（ホットリロード）
  - プロンプトファイルおよびエージェント設定ファイル（YAML）を編集した際、コンテナやプロセスの再起動を伴わずに次回リクエスト時から最新の内容が反映されること。

### FR-010 Memory管理（短期記憶・長期記憶）

AIエージェントは文脈維持とパーソナライズのため、スコープの異なる2種類の記憶領域を管理できること。

- 短期記憶（セッション単位：`chat_id`）
  - 同一チャットセッション内の会話履歴やツール実行の途中経過を保持し、連続した対話や作業の文脈を維持できること。
  - NFR-001 に基づくコンテキスト圧縮（スライディングウィンドウ・要約）と連動すること。
- 長期記憶（ユーザ単位：`user_id`）
  - チャットセッションを跨いで、ユーザの属性、業務上の好み、過去の重要な決定事項、頻出の前提条件などを永続化・抽出し、新しいチャット開始時にも自動参照できること。

### FR-011 RBAC（ロールベースアクセス制御）

AIエージェントは実行ユーザのロールに基づき、利用可能なエージェント・機能・データへのアクセス制御を行うこと。

- ロール定義と階層管理
  - 定義ロール例：`Admin`（システム管理者）、`PowerUser`（エージェント作成・高度ツール利用可）、`User`（一般利用者）、`Guest`（制限付き閲覧・質問のみ）
  - ロールの追加・変更や権限マッピングを外部設定ファイル等で柔軟に変更できること。
- エージェント利用制限
  - ユーザのロールに応じて、呼び出し可能なエージェント（モデルID）を制限できること。

### FR-012 Tool権限制御（ツール単位の実行認可）

AIエージェントは組み込まれた各ツールに対して、ロールおよびエージェント単位での実行可否を制御できること。

- ツール実行フィルタリング
  - エージェント初期化時およびツール呼び出し直前のフック処理において、実行ユーザのロールに許可されていないツール（例：GitLab更新、SSH実行、特定Difyナレッジ検索等）の実行をブロックすること。
- 実行前承認（Human-in-the-Loop）オプション
  - 外部システムへの書き込みやコマンド実行など影響の大きいツールについて、設定により実行前にユーザへ確認・承認を求めるフローを有効化できること。

### FR-013 所有権管理（データ分離・マルチテナント性）

AIエージェントは扱うすべてのデータに対して所有者（`user_id`）を紐付け、ユーザ間のデータ混在や不正参照を防止すること。

- 管理対象データ
  - 会話履歴（短期記憶）
  - 長期記憶データ
  - アップロードファイル（MCPサーバー上）
  - 生成ファイル（MCPサーバー上）
- アクセス境界の強制
  - すべてのデータ取得・検索・削除処理においてリクエスト元の `user_id` によるフィルタリングを強制し、他ユーザのデータにアクセスできないこと（`Admin` による監査目的の参照を除く）。

### FR-014 監査ログ（証跡記録・トレーサビリティ）

AIエージェントはセキュリティ監査および障害原因追跡のため、一連の実行履歴を改ざん困難な形式で記録すること。

- 記録対象項目
  - 実行日時、トレースID、`user_id`、`chat_id`、ユーザロール
  - 呼び出されたエージェント名・実行Workflow構成・使用LLMモデル名
  - 入力プロンプト概要、Tool実行履歴（ツール名・引数・実行結果・成否）
  - 最終出力ステータス、エラー発生時のスタックトレース・エラーコード
  - 消費トークン数（入力・出力）および処理時間

### FR-015 CLI・外部API実行（ヘッドレス利用）

AIエージェントは OpenWebUI を経由しないプログラムや開発ツールからも、統一された API 仕様で呼び出し可能であること。

- OpenAI互換APIエンドポイントの提供
  - `/v1/chat/completions` 等の標準的な REST API エンドポイントを公開し、IDE拡張（Continue 等）や社内システム、Pythonスクリプトから直接利用できること。
- メタデータの柔軟な指定
  - OpenWebUI 以外からの呼び出し時においても、HTTPヘッダやリクエストパラメータを通じて `user_id` や `chat_id` 等を指定でき、適切な権限・記憶管理のもとで実行できること。

### FR-016 ガードレール制御（入出力フィルタリング）

AIエージェントは設定ファイルでの選択に基づき、入力プロンプトおよび出力回答に対する安全性チェックを行えること。

- ガードレールポリシーの選択適用
  - エージェント単位で適用するガードレール（例：機密キーワード検出、PIIマスク、プロンプトインジェクション検知、禁止コマンド検知）を設定ファイルで有効化・切り替えできること。
- 検知時のアクション制御
  - 違反を検知した際、処理を即座にブロックして警告メッセージを返すか、該当箇所をマスキングして処理を継続するかをポリシーごとに設定できること。

### FR-017 トークン使用量計測・集計（メータリング）

AIエージェントはローカルLLMおよび外部LLMの利用状況を把握するため、リクエスト単位のトークン消費量を計測・記録できること。

- トークン計測と記録
  - LiteLLM のレスポンス等から入力トークン数・出力トークン数（およびキャッシュヒットトークン数）を取得し、`user_id`・エージェント名・モデル名と紐付けて記録すること。
- 上限アラート・クォータ制御（オプション）
  - ユーザ別または日次・月次のトークン利用上限を設定した場合、しきい値超過時の警告出力や利用制限を行えること。


### 4. 非機能要件

#### NFR-001 性能要件

ローカルLLMの推論特性およびマルチステップのエージェント実行を前提とした応答性・処理能力を担保すること。

- ストリーミング応答
  - ユーザの体感待ち時間を短縮するため、OpenWebUIへの回答出力は原則としてストリーミング形式で逐次返却できること。
  - ワークフロー実行中（PlannerやTool実行中）の進捗ステータスについても、必要に応じてストリーミング出力または中間メッセージとして通知できること。
- タイムアウト制御
  - ローカルLLMによる長文生成や複数ステップのワークフロー実行を考慮し、OpenWebUI・LiteLLM・AIエージェントAPI間の通信タイムアウトは十分に長く設定可能とすること（推奨値：300秒〜600秒）。
  - 外部連携（Dify、MCPサーバー、GitLab等）のツール実行には個別のタイムアウト値を設定でき、ハングアップを防止できること。
- 同時実行制御
  - ローカルLLMによるGPUリソース枯渇を防ぐため、AIエージェント側またはLiteLLM側で同時リクエスト数を制御（キューイングおよびレート制限）できること。
- ファイル処理上限
  - アップロード解析および生成対象のファイルサイズ上限（例：1ファイルあたり50MBまで）および同時処理ファイル数を設定ファイルで制限できること。
- コンテキスト長・トークン上限管理
  - ローカルLLMの最大コンテキスト長を超過して推論エラーとなることを防ぐため、LLMへの送信前に総トークン数を見積もり、上限閾値（例：モデル上限の80%）内に収まるよう自動調整できること。
  - OpenWebUIからの長い会話履歴や、Continue等から送信される大容量のソースコード・複数ファイルに対して、以下のコンテキスト圧縮・削減機構を設定ファイルで選択・組み合わせられること。
    - スライディングウィンドウ方式（直近Nターンのみ保持し、古い履歴を破棄）
    - 要約圧縮方式（過去の会話履歴やツール実行結果をLLMで要約して圧縮）
    - 大容量入力のチャンク分割・関連箇所抽出（ファイル全文を一度にプロンプトへ展開せず、必要な範囲のみ参照）
  - 圧縮・切り詰めを行ってもなおモデルのコンテキスト上限を超える場合は、LLMへ無理にリクエストを送信せず、ユーザへ入力削減や新規チャット作成を促す分かりやすいエラーメッセージを返却できること。
- 推論キャッシュの活用（KVキャッシュ・プロンプトキャッシュ）
  - ローカルLLMの初回トークン生成時間（TTFT）を短縮するため、推論エンジン側（vLLM、Ollama等）またはLiteLLM側のKVキャッシュ・プロンプトキャッシュ機構を有効に活用できるプロンプト構造とすること。
  - キャッシュヒット率を高めるため、動的に変化する情報（現在時刻、ユーザ固有のコンテキスト、検索結果等）はシステムプロンプトの先頭ではなく、会話履歴の末尾またはユーザメッセージ側に配置する設計とすること。
  - コンテキスト圧縮（履歴の削除・要約）を行う際は、キャッシュの再計算コスト（キャッシュミス）が最小限となるよう、圧縮の実行タイミング（しきい値）を設定ファイルで調整可能とすること。

#### NFR-002 可用性・信頼性要件

閉塞NW環境における自立稼働と、障害発生時の影響を最小限に抑えるための構成とすること。

- 完全オフライン稼働（閉塞NW対応）
  - インターネットへの外部通信を一切行わずに起動・稼働できること。
  - Strands Agents等のフレームワーク標準のテレメトリ外部送信機能はデフォルトで無効化すること。
  - トークナイザーやドキュメント解析ライブラリ等が必要とする辞書・モデルデータは、すべてDockerイメージビルド時に事前組み込み（キャッシュ）済みであること。
- 外部ツール障害時の縮退・リトライ動作
  - Dify検索やMCPサーバ等のツール呼び出しで一時的な通信エラーが発生した場合、設定された回数・間隔で自動リトライを行えること。
  - 一部のツールが利用不可であってもエージェントプロセス全体はクラッシュせず、ユーザへエラー状況を適切に回答できること。
- LLM出力異常への耐性
  - ローカルLLMが不正な形式のTool呼び出し（JSON構文エラー等）を出力した場合、自動的にエラー内容をLLMへフィードバックし、自己修正リトライを行えること。

#### NFR-003 セキュリティ要件

閉塞NW内での権限分離、データ保護、および安全なツール実行を担保すること。

- 認可およびセッションコンテキストの検証
  - OpenWebUIのPipe Functionから引き渡されたメタデータ（user_id、chat_id、file_id、ロール情報）を検証し、リクエスト単位で厳格に分離して扱うこと。
  - 別ユーザのセッション記憶やファイルへの不正アクセスを防止すること。
- 入力・出力ガードレール
  - プロンプトインジェクション攻撃や機密情報の不適切な出力を検知・遮断するガードレール機構を、設定ファイルで有効化・選択できること。
- ツール実行の安全性
  - SSH実行やコード実行、ファイル操作などの高権限ツールは、許可された対象ホスト・ディレクトリ範囲内でのみ実行できるよう制限できること。
  - 破壊的操作（データ削除・本番環境への書き込み等）を伴うツールについては、実行前の確認フローまたはロール制限を強制できること。
- ファイル配信のアクセス制御
  - MCPサーバ経由で発行される生成ファイルのダウンロードURLは署名付きURLとし、有効期限を設定できること。
- 認証情報の保護
  - LiteLLM、Dify、MCPサーバ、GitLab等のAPIキーや認証情報はソースコードや設定ファイルに直接記載せず、環境変数またはシークレット管理機構から注入すること。

#### NFR-004 運用性・保守性要件

開発者によるエージェント構築の容易さと、運用者の監視・トラブルシューティングを容易にすること。

- ローコードによるエージェント開発・変更
  - 新規ユースケースの追加や既存エージェントの振る舞い変更（プロンプト、使用モデル、利用ツール、ワークフロー順序）は、Pythonコードの改修ではなく設定ファイル（YAML等）およびプロンプトファイルの編集のみで完結できること。
  - システムプロンプトおよび設定ファイルの変更は、コンテナの再起動なしで反映できること。
- 標準化されたデプロイ手順
  - 閉塞NW環境へ持ち込み可能なDockerイメージのビルド手順、およびコンテナ起動・更新手順がテンプレートとして整備されていること。
- 可観測性（ログ・トレース・メトリクス）
  - リクエスト単位で一意のトレースIDを発行し、FastAPI〜Strands〜LLM〜各ツール実行までの一連の処理経路とエラー原因を追跡できる構造化ログ（JSON形式等）を出力すること。
  - ユーザ別・エージェント別・モデル別のトークン消費量（入力・出力トークン数）および実行時間を計測・出力できること。
- データのライフサイクル管理
  - 短期記憶、アップロードファイル、MCPサーバ上の一時生成ファイルについて、保持期間（TTL）を設定でき、期限切れデータを自動削除する機構を備えること。
  - 監査ログおよび長期記憶は永続化ストレージへ保存し、定期バックアップの対象とすること。

#### NFR-005 拡張性・移植性要件

将来的な機能追加や、オンプレミスからパブリッククラウド・他部署案件への横展開を見据えたアーキテクチャとすること。

- クラウド・実行環境への移植性（マルチクラウド対応・過剰実装の分離）
  - エージェントのコアロジック（YAMLワークフロー定義、プロンプト、Strandsによる自律制御、MCPツール）と、インフラ依存層（Web API、認証、ストレージ、記憶領域）を明確に分離したアーキテクチャとすること。
  - 将来的にセキュリティ要件の異なる他案件・他部署へ展開する際、コアロジックや業務ツールをそのまま流用し、AWS（Bedrock AgentCore）、Azure（Azure AI Agent Service）、GCP（Vertex AI Agent Engine）等のマネージド基盤へアダプター層の差し替えのみで移植可能とすること。
  - 同時実行制御、推論キャッシュ、セッション記憶管理などの基盤機能は、閉塞NW環境ではフレームワーク側のミドルウェア等で制御し、パブリッククラウド環境では各クラウドのマネージド機能へ委譲できる設計とすること。
- モデルプロバイダの切り替え容易性
  - LiteLLMの抽象化層を介することで、ローカルLLM（Ollama、vLLM等）からパブリッククラウドLLM（Amazon Bedrock、Azure OpenAI、Claude、Gemini等）へ設定変更のみで切り替えられること。
- ツールのプラグイン拡張性
  - 新規ツールを追加する際、Strands標準の `@tool` デコレータ形式またはMCP（Model Context Protocol）サーバーとして実装することで、プラットフォーム側のコアコードを変更せずに組み込めること。

| :--- | :--- | :--- | :--- | :--- |
| **実行ランタイム・同時実行・タイムアウト** | FastAPI + Uvicorn + 自前キュー制御 | AgentCore Runtime（自動スケール・長時間対応） | Azure AI Agent Service（マネージド実行環境） | Vertex AI Agent Engine（マネージド実行環境） |
| **推論キャッシュ（KV / Prompt Cache）** | vLLM等の設定・自前最適化 | Bedrock Prompt Caching（自動KVキャッシュ） | Azure OpenAI Prompt Caching（自動プレフィックスキャッシュ） | Vertex AI Context Caching（明示的/暗黙的キャッシュ） |
